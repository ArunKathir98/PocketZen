6 · State management and handlers

6.1 The data document

emptyData() in lib/defaults.js defines the whole document. It is the only thing that is saved, synced, exported and merged.

{
  version: 1,
  updatedAt: 0,                  // ms timestamp of the last change — drives sync decisions
  accounts:     [],              // { id, name, type, balance (opening), color, note }
  categories:   [],              // { id, type:'income'|'expense', name, icon, color }
  transactions: [],              // { id, type:'income'|'expense'|'transfer', amount, accountId, toAccountId,
                                 //   categoryId, note, date:'YYYY-MM-DD', time:'HH:mm' }
  budgets:      [],              // { id, categoryId, amount, period:'monthly' }
  reminders:    [],              // { id, title, amount, dueAt, repeat, until, doneCount }
  emis:         [],              // { id, name, lender, totalAmount, totalMonths, emiAmount, startDate, paidBefore, payments[], accountId }
  people:       [],              // { id, name, note }
  loans:        [],              // { id, personId, direction:'lent'|'borrowed', title, startDate, interest{…}, dueDate, remind, note, events[] }
  groups:       [],              // groups I belong to: { id (Drive file id), name, role:'admin'|'viewer', me, joinedAt }
  settings: { currency, dailyReminder, dailyReminderTime, showEmi, showReminders,
              showLoans, showGroups, notifySound, lastBackupAt },
  pin: null                      // { salt, hash, recovery? } — never exported
}
Account balances are not stored. They are computed on demand (calc.accountBalance = opening balance + income − expense ± transfers). Storing derived values would let them drift from the records; computing them cannot.
One document, not many tables. A personal finance dataset is small (a few thousand records). One JSON object is trivial to persist, export, import, merge and sync as a single Drive file. A normalised database would add complexity with no benefit at this size.

Every record has an id created by uid() (crypto.randomUUID()). Ids are what make merging two documents safe (chapter 7).

6.2 store.jsx — the provider

AppProvider owns this React state:

StateMeaning
sessionWho is signed in (pz:session), or null. Mode is 'google' or 'local'.
dataThe live document.
readyFalse until the document has loaded from IndexedDB.
lockedTrue while the PIN screen must be shown.
syncidle | local | syncing | synced | offline | auth | error — drives the status pill and the "Reconnect" banner.
loggingIn, errorLogin button state and message.

and these refs: dataRef and sessionRef (always the latest value, safe to read inside async callbacks), pushTimer, pushing.

Why refs next to state? Async code (a push that awaits Drive) would otherwise read a stale data captured by its closure. dataRef.current is updated synchronously inside commit, so a sync that finishes seconds later still sees the user's newest edit.

6.3 The one write path: commit()

const commit = useCallback((fn) => {
  const s = sessionRef.current
  const next = { ...fn(dataRef.current), updatedAt: Date.now() }
  dataRef.current = next            // 1. latest value for async code
  setData(next)                     // 2. re-render now
  if (s) {
    persistLocal(s.sub, next)       // 3. IndexedDB  data:<sub>
    if (s.mode !== 'local') {
      localStorage.setItem(dirtyKey(s.sub), '1')   // 4. "Drive is behind"
      schedulePush()                // 5. debounce 1.5 s → push()
    }
  }
}, [...])

Everything the UI can change goes through it via the small API below, so there is exactly one place to look for "who changed the data".

Usage in a page is deliberately boring:

const { data, add, update, remove } = useApp()

update('budgets', budget.id, { amount: 9000 })

6.6 Other contexts and hooks

  • DialogProvider / useDialog() (components/dialog.jsx): await confirm({title, message, confirmText, danger}), await alert({...}), await choose({ actions:[{label,value,variant}] }). One dialog at a time, Escape cancels (resolves null). These replace window.confirm, which looks out of place in an installed app and cannot offer three choices.
  • useInstall() (lib/install.js): exposes canPrompt, ios, installed and prompt().
  • useGroup(id, role, hint) (lib/useGroup.js): see chapter 10.
A real bug we hit: after introducing useDialog, one button still called confirm('Log out?') with a plain string. The function returns a Promise, which is always truthy, so the button logged the user out immediately without asking. Always await the dialog helpers.
