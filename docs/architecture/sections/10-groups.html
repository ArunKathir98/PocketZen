10.1 The requirement and the design journey

Requirement: a group (trip, flat, event) with people, expenses and payments; suggested payments to settle up; a PDF summary; and a way to invite friends.

AttemptIdeaOutcome
v1 — serverA Cloudflare Worker with one Durable Object per group, anyone with an id could join and edit.Worked and was tested (25 concurrent edits, no lost update) — but it introduced a backend, which contradicted "no server" and brought hosting/privacy questions.
v2 — Drive-hosted (current)The group is a file in the admin's own Google Drive. The admin edits. Everyone else gets a view-only link.No server, no database. Matches the privacy promise. Trade-off: only the admin can change things.
The product owner chose simplicity: "no backend, joined users just view, admin has all the rights". That removed the hard part of collaboration (concurrent writers) and let us reuse Drive as storage. wrangler.jsonc still carries a migration that retires the old GroupDO class so the Cloudflare deploy stays clean.

10.3 The group document (groupState.js)

{ id, name, currency, createdAt, updatedAt, version,
  members:  { [id]: { id, name, email, deleted, u } },
  events:   { [id]: { id, name, deleted, u } },
  expenses: { [id]: { id, title, amount, paidBy, split:[memberId], eventId, date, note, deleted, u } },
  payments: { [id]: { id, from, to, amount, date, note, settle, deleted, u } } }

Every entity has u (last-updated ms). Deleting sets deleted:true (a tombstone), so a deletion also wins over an older edit.

Operations and last-write-wins

Changes are small idempotent operations: { t:'set', c:'expenses', id, v:{…} } or { t:'meta', v:{ name } }. applyOps(state, ops, now) validates each one (cleanEntity: allowed fields only, id format, amount 0–1e9, date format, ≤ 2000 bytes, timestamps clamped to now + 60 s), ignores an op if the stored entity is newer, increments version when something changed, and enforces limits (60 members, 50 events, 3000 expenses, 3000 payments, 1 MB total). It never mutates its input. The same function is used when the admin saves and when the UI overlays unsaved edits on top of the last known state.

10.4 Money maths

  • Minor units. toMinor(x) = round(x × 100); all group arithmetic is on integers, so no floating-point drift.
  • splitEqual(total, ids): base = ⌊total/n⌋; the first total − base×n people get one extra cent, so the parts always sum to the total.
  • computeBalances: per person paid, share, sent, received; net = paid − share + sent − received (positive = the group owes them). Net always sums to 0.
  • suggestSettlements: repeatedly match the largest debtor with the largest creditor and transfer min(debt, credit) until all are zero. At most n − 1 payments, deterministic ordering.
  • Settle-up checkboxes: ticking a suggestion creates a payment (settle:true); balances shrink and the suggestion disappears; unticking deletes that payment. The checkbox is the UI for a real payment record.

10.5 Lifecycle: create → share → view

Figure 10.1 — Admin, Drive and viewer. Nothing in this picture is a PocketZen server.

1

Create

enableGroupScope() (first group only) → build a draft with the admin as the first member → createGroupFile() (multipart upload, private) → writeGroupFile() again so the real file id is stored inside → cache in IndexedDB → add('groups', { id, name, role:'admin', me }).

2

Edit (admin)

Forms call dispatch(ops) from useGroup. Ops go into an outbox (IndexedDB) and are applied optimistically on screen. The sync step re-reads the file, applies the outbox on top of what is in Drive (the admin may use several devices), and writes it back. Offline edits wait in the outbox.

3

Invite

Tapping Invite calls shareGroupFile() (permissions.create role reader, type anyone, allowFileDiscovery:false) and shows the link …/?view=<fileId>. Until then the file is private.

4

View

Opening the link: capturePendingJoin() stores the id; App.jsx shows PublicGroup (no session) which renders GroupView with a viewer entry. readPublicGroupFile(id) fetches files/<id>?alt=media&key=API_KEY — no token. Polls every 30 s; keeps a cached copy for offline.

5

Save to my list (viewer with Google)

Groups → Join accepts a link or id, reads the file, optionally lets the person pick "which one are you?" (to show their own balance) and stores a viewer entry.

6

Delete

deleteGroupFile() removes the file; viewers see "This group isn't available".

10.7 The sharing switch and the API key

Viewing by link needs a Google API key compiled into the app (VITE_GOOGLE_API_KEY). groupSharingEnabled() = GROUP_SHARING && hasApiKey(). When it is false: the Join and Invite buttons disappear, group links are ignored and groups remain a private, admin-only tool. Setting the key at build time turns sharing on with no code change; a constant in src/config.js can force it off. Error messages distinguish no key, key rejected by Google (wrong referrer restriction, Drive API not enabled) and group not found.

10.8 The PDF summary (groupPdf.js)

  1. A Doc class draws A4 pages (794×1123 CSS px, rendered at 2×) on <canvas>: gradient header with logo, stat tiles, then tables (balances, suggested payments, payments recorded, every expense) with wrapping text, zebra rows, repeated table headers on a new page and "Page n of N" footers.
  2. Each canvas becomes a JPEG (canvas.toBlob, quality 0.92).
  3. pdfFromJpegs() writes a minimal PDF 1.4: catalog, pages, and per page a page object, an image XObject (/DCTDecode) and a content stream drawing it full-page; then the xref table and trailer.
  4. shareOrDownloadPdf() uses the share sheet when it accepts files, else downloads.
Why canvas and not a PDF library? Standard PDF fonts cannot show "₹" or Tamil/Hindi/Chinese names. The browser can, so we let it render the text and embed the picture. Trade-off: the text in the PDF is not selectable. Tested with 90 expenses → 4 valid pages with mixed scripts.
