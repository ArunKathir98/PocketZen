8 · Authentication and security

8.1 What "login" means here

PocketZen has no user accounts of its own. "Logging in" means getting permission from Google to read and write files in the user's Drive, using Google Identity Services (GIS), token model. The browser asks Google for an access token; the token is then sent as Authorization: Bearer … on Drive REST calls made directly from the browser.

Why the token model and not "Sign in with Google" ID tokens or the code flow? An ID token proves who you are but gives no Drive access. The authorization-code flow gives long-lived refresh tokens, but needs a server to keep a client secret, and we have no server. The token model needs no secret and no server. The price is that tokens last only about an hour and cannot be refreshed silently in the background without a window (see 8.4).

Most users only ever see the basic permission. The extra Drive permission appears only for people who create a group, at the moment it makes sense.

// google.js
export async function requestToken({ prompt = '', hint, scope } = {}) {
  const oauth2 = await waitForGis()            // the GIS script from index.html
  return new Promise((resolve, reject) => {
    oauth2.initTokenClient({
      client_id: CLIENT_ID, scope: scope || scopes(), hint, prompt,

                            saveToken(); resolve(token) },
      error_callback: (err) => reject(new Error(err?.type)),
    }).requestAccessToken()                      // opens Google's window
  })
}
  • login() uses prompt: 'select_account' (shows the account chooser) → fetchProfile() → startSession({ ...profile, mode:'google' }).
  • The session (pz:session) has no expiry. It lasts until the user logs out, which satisfies "keep me signed in".
  • loginLocal() creates { sub:'local', mode:'local' } and skips Google entirely.

8.4 Tokens: caching and renewal

Because there is no refresh token, every hour the app must ask Google again. That request opens a (usually auto-closing) window. Two rules keep this unobtrusive:

1

Cache the token

The token and its expiry are stored in localStorage['pz:tok']. At module load, a token valid for more than one more minute is restored. Reloading, refreshing or reopening the installed app within the hour therefore reuses it: no window. The cache is cleared on logout and on a 401.

2

Background work never opens the window

hasLiveToken() is checked before any timer, focus or "back online" sync. Only launch, a user action (saving an edit, tapping Reconnect, opening a group) or an explicit button may request a new token.

What users saw before: the token lived only in memory, so every page load opened Google's sign-in window. A test counting requestAccessToken() calls now shows: first launch 1, three reloads 0, expired token 1, focus/online with an expired token 0, saving an edit 1.
A token in localStorage is readable by any script on the same origin, so an XSS bug could steal it for up to an hour. The scopes are narrow (app data and files the app created) and the app contains no third-party scripts besides Google's, which is the usual accepted trade-off for a browser-only OAuth app.

8.5 Calling Drive: the api() helper

async function api(url, opts, hint) {
  const t = await ensureToken(hint)                   // cached → else renew
  let res = await fetch(url, { ...opts, headers: { Authorization: `Bearer ${t}` } })
  if (res.status === 401) { forgetToken(); /* renew once, retry */ }
  if (!res.ok) throw Object.assign(new Error(`Google API ${res.status}`), { status: res.status })
  return res
}

8.6 The PIN lock

PieceDetail
Storagedata.pin = { salt, hash, recovery? }; the PIN itself is never stored.
HashinghashPin: PBKDF2-SHA-256, 150 000 iterations, 16-byte random salt, 256-bit output (Web Crypto). verifyPin recomputes and compares.
When it locksOn launch if a PIN exists, and when the tab has been hidden for 60 seconds or more.
Brute forceFive wrong attempts → 30-second wait (PinLock.jsx). A 4-digit PIN is a casual-privacy lock, not strong security, and the UI does not claim otherwise.
Forgot PIN (Google)reverifyAccount(sub): sign in again with select_account and require the same sub; then choose a new PIN. No email and no extra permission.
Forgot PIN (local)A one-time recovery code (12 characters from a 32-letter alphabet without 0/O/1/I, shown as XXXX-XXXX-XXXX) is created when the PIN is set. Only its salted PBKDF2 hash is stored. Entering it allows a new PIN. If both are lost, the only way in is "erase data".
History: the first design emailed a 6-digit code through the Gmail API. That needs the sensitive gmail.send scope, which forces Google's verification process. Re-verifying with Google proves identity just as well and needs no extra scope, so the email flow was removed.

8.7 Encrypted backups

  • Plain backup: JSON of the document without the PIN (buildBackup).
  • Protected backup: { app, encrypted:true, v:1, salt, iv, data } — AES-GCM, 256-bit key derived from the password with PBKDF2-SHA-256 (200 000 iterations), random 16-byte salt and 12-byte IV. A wrong password fails authentication (bad_password); a missing one raises password_required.
  • saveBackupFile shares through the phone's share sheet when it accepts files, otherwise downloads. The file is typed text/plain because far more share targets accept it than application/json.

8.8 Public identifiers in the bundle

VITE_GOOGLE_CLIENT_ID and VITE_GOOGLE_API_KEY are compiled into the JavaScript. That is normal for a browser app and safe if configured correctly: the client id only works from the authorised origins, and the API key should be restricted to your website and the Drive API in Google Cloud. No secret exists in this project.
