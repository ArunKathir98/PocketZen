7 · Persistence and Drive sync

7.1 On-device storage: idb.js

A 60-line wrapper turns IndexedDB into three promise functions: idbGet(key), idbSet(key, value), idbDel(key). One database (pocketzen), one object store (kv). If IndexedDB is unavailable (some private modes) it silently falls back to localStorage under pz:kv:<key>.

IndexedDB keyContent
data:<sub>The user's document (sub = 'local' for no-account users).
group:<fileId>Last known state of a shared group (works offline).
outbox:<fileId>The admin's group edits not yet saved to Drive.
Why IndexedDB and not localStorage? localStorage is synchronous, limited to roughly 5 MB, and stores only strings. IndexedDB is asynchronous, has a far larger quota and is the better target for the browser's "persistent storage" request. Small flags still live in localStorage because they must be readable synchronously at startup (session, theme, token).
Migration. Early versions kept the document in localStorage['pz:data:<sub>']. loadData() in store.jsx moves it into IndexedDB the first time it finds one, then deletes the old copy.

7.2 Cloud storage: the Drive app-data file

For Google users the same document is stored as pocketzen-data.json in the app-data folder of their Drive. That folder is hidden, private to this OAuth client and invisible in the normal Drive UI (drive.appdata scope). google.js exposes two calls:

  • driveLoad(sub, hint) — find the file (id cached in pz:fileId:<sub>), download JSON; null if none exists.
  • driveSave(sub, data, hint) — update the file with PATCH …?uploadType=media, or create it with a multipart upload the first time.

7.3 Dirty and synced markers

Key (localStorage)Meaning
pz:dirty:<sub>Set on every commit; cleared after a successful push if nothing changed in the meantime. "This device has changes Drive hasn't seen."
pz:synced:<sub>The Drive file's updatedAt that this device last saw or wrote. Used to detect that someone else wrote to Drive since.

7.4 The two halves of sync

pull() — run at launch and when the app returns to the foreground

  1. Load the Drive document (remote).
  2. If remote.updatedAt > local.updatedAt and this device is not dirty → adopt the remote document (persist to IndexedDB, set synced).
  3. Else if there is no remote, or the device is dirty, or local is newer → call push().
  4. Else they are identical → just record synced.

push() — runs after edits (debounced)

  1. Re-read the Drive file. If its updatedAt is newer than pz:synced, another device wrote since we last synced: compute merged = mergeData(remote, local) (settings and PIN preferring local), replace local state with it.
  2. driveSave the (possibly merged) document and record synced = its updatedAt.
  3. If the user edited again while the upload ran, keep dirty and schedule another push; otherwise clear it.
The bug this design fixes. The first version simply uploaded the local document. With two devices open, the one holding an older copy overwrote the other's newer changes (a record added on the phone vanished when the laptop saved). It surfaced to the user as "data deleted on refresh". The reproducing test used a fake Drive shared by two browser contexts. The fix is the read-merge-write in step 1 above.

7.5 mergeData(base, inc) — combine without duplicates

The same function is used by the push merge, by "Connect Google Drive" when Drive already has data, and by importing a backup in "Merge" mode.

CollectionRule
accountsMatched by id or case-insensitive name; the incoming duplicate is dropped and its id remapped.
categoriesMatched by id or (type + name). So two "Salary" income categories from two fresh installs become one.
transactionsDedupe by id; accountId / toAccountId / categoryId remapped to the kept ids.
budgetsOne per category.
emis, remindersUnion by id (EMIs' account remapped).
people, loansPeople matched by name; loans union by id with personId and event accountId remapped.
groupsUnion by id.
settings, pinBase settings; optional-page flags OR-ed; PIN from whichever side has one.
Deliberate trade-off: a merge is a union, so it never loses data but cannot know about deletions. If device A deletes a record and device B (stale) edits something, the record can come back. We chose "never silently lose money records" over "never resurrect a deleted one". Real per-record tombstones would fix it at the cost of more code; the group engine (chapter 10) does use per-entity timestamps because its data is smaller and more structured.

7.6 Offline behaviour

  • Reads and writes always hit IndexedDB, so the app is fully usable offline.
  • While offline, push() fails; the status becomes offline, dirty stays set.
  • When the device is back online (and a token is valid) or the user taps Reconnect, the next push merges and uploads.
  • The service worker precaches the app shell, so the page itself loads without a network.

7.7 Switching between local and Google (CloudCard.jsx)

  1. Offer a backup file first (optional).
  2. Sign in, then driveLoad.
  3. If Drive has user data, ask: Merge both (default, mergeData(remote, local)) · Keep Drive data only · Replace Drive with this device · Cancel.
  4. switchToGoogle(profile, next) writes next under the Google sub, marks it dirty and removes the local copy. The normal push then uploads it.

The reverse, disconnectGoogle(), keeps a complete copy on the device and never touches the Drive file.
