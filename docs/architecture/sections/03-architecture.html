3 · Architecture at a glance

3.1 The seven layers

Think of the code as seven layers. Each layer mostly talks to the one directly below it, which is what keeps the app understandable.

Figure 3.1 — Layers of PocketZen. Most pages only call the store or a pure function. The group screens (Groups, GroupView) and CloudCard also call google.js and the IndexedDB helper directly, because group data is separate from the personal document.

3.2 One document, three places

All personal data is one JSON object (the "document"). It is kept in up to three places, and understanding which is which explains most of the code:

PlaceHoldsWritten by
React state (data)The live copy the UI renders. Mirrored in a ref (dataRef) so async code always sees the latest value.commit()
IndexedDB data:<sub>The durable on-device copy. The app starts from it, so it works offline and loads instantly.persistLocal() after every commit
Drive pocketzen-data.jsonThe cloud copy (Google users only), in the hidden app-data folder. Lets several devices share data.push() / read by pull()
Local first. The UI never waits for the network. A change shows immediately, is saved to IndexedDB in milliseconds, and Drive catches up in the background. If Google is unreachable the app keeps working and syncs later.

When a bug is about numbers (interest, balances, splits) you only ever open a pure module. When it is about sync or sign-in you open store.jsx / google.js. When it is about looks you open a page and styles.css.

3.5 Two kinds of shared state

  • Personal data (accounts, records, budgets, EMIs, loans, reminders…): one document per user, managed by store.jsx, synced as a whole file.
  • Group data: one document per group, a separate file in the admin's Drive, managed by useGroup.js with its own cache and outbox. They are kept separate because they have different owners, audiences and sync rules (chapter 10).
